Voyager
Teardown

Turning a LinkedIn profile URL into structured JSON by speaking the private Voyager API directly. The pipeline now runs end to end — here is what it extracts, which forks in the road were taken, and what to read to follow the reasoning.

The whole problem, in one string
/* Rest.li query grammar. Structure stays raw. Data gets escaped. */

variables=(profileUrn:urn%3Ali%3Afsd_profile%3AACoAA…,sectionType:EXPERIENCE)
          ^ ^          ^                              ^
          structural delimiters — these must NOT be encoded

Encode them all (URLSearchParams) → HTTP 400.
Encode none of them (raw URN colons) → HTTP 400.
Encode exactly % : ( ) , inside values only → HTTP 200.

That asymmetry is not documented anywhere. It was read off a browser request that returned 200 and pinned down in test/restli.test.ts against the captured string, byte for byte.

01 — Where it stands

A URL goes in, a typed record comes out

As of the latest run the whole chain works: guard the URL, mint a session, resolve the slug to a URN, pull twelve Rest.li collections, merge them into one entity graph and extract a validated profile record. What is still missing is the HTTP service around it.

Three modules landed since the last revision of this page: linkedin/normalized.ts resolves Voyager's URN graph, linkedin/extract.ts maps entities onto our own types, and schema.ts defines that contract in Zod. Sixteen tests pass against synthetic fixtures; tsc --noEmit is clean.

02 — The fetch path

What happens to a URL

A stranger hands the service a URL and the service makes an HTTP request. That is the textbook SSRF setup, so the pipeline is built so the stranger's string never becomes a fetch target.

Two cookies, four headers

Authentication is smaller than it looks. li_at is the session. JSESSIONID looks like "ajax:123…", quotes included. The csrf-token header is that same value with the quotes stripped — LinkedIn stores no per-session CSRF token, it just checks that a header matches a cookie.

That is the double-submit cookie pattern, and it works against a cross-site attacker precisely because the browser attaches the cookie automatically while same-origin policy stops attacker JavaScript from ever reading it. Holding both values off-browser satisfies the check by copying one into the other — which is exactly why these two strings are a password.

The four headers that matter
cookie: li_at=<session>; JSESSIONID="ajax:123…"
csrf-token: ajax:123…              ← same value, quotes stripped
x-restli-protocol-version: 2.0.0   ← omit → (a:b) parsed under v1 rules, silently
accept: application/vnd.linkedin.normalized+json+2.1

The accept header is load-bearing. It swaps a deeply nested document
for a flat included[] array plus a tree of URN references — which is
exactly the shape normalized.ts is built to walk.

Paced like a person, not a script

The capture that seeded this project showed 49 requests over 164 seconds: tight bursts under half a second apart, separated by pauses of 4, 8, 31, 43 and 48 seconds. That is someone scrolling and reading.

So fetch-profile.ts fires the core query, the full profile and the first six collections in a burst, pauses 5–9 seconds as if scrolling, then fires the remaining six. The live run took roughly 25 seconds for fourteen requests and drew no block signal. A uniform delay between every request would be less human than this, not more.

03 — Two routes in

Component tree vs typed entity

There were two ways to ask Voyager for a profile's sections. They return fundamentally different things, and picking the right one decided whether the extractors would be a hundred lines or a thousand.

How the collection route was found

Not by guessing endpoint names. The HAR capture contained one non-GraphQL call shaped /identity/dash/profiles/<urn>?decorationId=…FullProfile-76, which proved the identity/dash/<collection> pattern was live. That projection returns the profile's scalar fields but no positions or educations — so those had to be separate collections.

Rest.li exposes collections through named finders selected by q=, and the collection names mirror the reference keys visible on the Profile entity itself: *profilePositionGroups, *experienceCard, *educationCard. Twelve were inferred from that convention. The latest run confirms every one of them resolves — the six that returned nothing answered successfully with nothing rather than 400.

The FullProfile projection earns its place separately: it is the only source of summary, which is the About section. The GraphQL vanityName query does not return it at all.

04 — Graph to record

Fourteen responses, one entity graph

Voyager's normalized representation is a flat graph, not a document. Everything lives in included[], and the tree points at it by URN string. Reading it is a two-step: index, then walk.

On the live run, eight saved responses carried 43 included[] rows that merged into 41 unique entities — the same Geo objects appear in more than one response. Merging every response into one graph means an entity resolves no matter which call happened to carry it.

Our shape, not theirs

schema.ts is an anti-corruption layer, and that is the whole point of it. LinkedIn's shape is unstable; ours is not. When a field is renamed or a projection bumps its version number, the change is absorbed in the extractors and the published contract does not move. The response is versioned under /v1/ so it can.

The contract also refuses to invent precision. A LinkedIn date is genuinely partial — positions carry {year, month}, educations often only {year} — so PartialDate keeps day nullable rather than padding it to the first of the month. Padding would make a real 1st-of-the-month indistinguishable from a guess.

The coverage contract — how “when available” is answered precisely
present: string[]   the section returned entities
empty:   string[]   upstream answered successfully with nothing —
                     the member has none, OR the collection name is
                     wrong and fails silently. We cannot tell those
                     apart, and say so rather than implying we can.
failed:  { section, reason }[]  the request itself errored

Returning [] for all three would be a lie of omission. A caller needs
to know the difference between "no certifications" and "we could not
find out whether there are certifications".
05 — Decisions & alternatives

Forks in the road

Each of these had a cheaper option that would have worked most of the time. The cases where “most of the time” is not good enough are what the choice is about.

Parse and rebuild, never validate and forward

The guard does not sanitise a URL and pass it along. It parses the input, extracts one field, throws the rest away, and lets the caller rebuild a request from a hardcoded template.

Chosen
Extract slug, discard input. A control that structurally cannot fail rather than one that mostly works.
Alt
Validate the URL, then fetch it. Every published bypass — userinfo, backslash, tab-stripping, double encoding — targets exactly this shape.
Alt
Regex the URL apart. Hand-rolled URL splitting is the single most reliable source of these bugs. new URL() also lowercases the host and punycodes IDN homographs for free.
Cost
Only /in/<slug> works. Company pages, jobs and posts each need their own parser.

Validate inside the lookup the socket actually uses

The naive SSRF check resolves the hostname, inspects the address, then calls fetch — which resolves again. An attacker serving a 0-second TTL answers public first and loopback second.

Chosen
Supply undici's lookup. Resolve once, validate every record, hand back that same answer. There is no second lookup to poison.
Alt
Pre-flight dns.resolve. The classic TOCTOU. Protects nothing against rebinding.
Alt
Hostname allowlist only. Meaningless at the IP layer — evil.com can hold an A record for 127.0.0.1.
Alt
Egress firewall / NAT policy. Genuinely stronger, and orthogonal. Worth adding in production; it just cannot live in the repo.

Fail closed on any bad record, not the first good one

A multi-record answer where any address is private is rejected outright, rather than selecting a permitted one.

Chosen
Reject the whole answer. A rebinding attacker can return a public and a private address together and let the client's selection logic pick wrong.
Alt
Filter to the allowed records. Introduces a selection step the attacker gets to influence.
Note
Unparseable, empty and non-unicast answers all reject too. Failing closed is the only correct default in a security check.

Never follow a redirect

undici is configured with no redirect handling and every call sets redirect: 'manual', so a 3xx arrives as an ordinary response and the client decides what it means.

Chosen
Classify, never follow. For Voyager a redirect is never data — it is a dead session or a challenge. It also leaves 302 → 169.254.169.254 nowhere to go.
Alt
Follow with a hop limit. Re-validating each hop is doable, but the first URL being safe says nothing about the third.
Payoff
Six honest failure kinds instead of one opaque error. A login redirect and a checkpoint redirect mean very different things — one is a stale cookie, the other is a flagged account.

Merge every response into one graph

A profile fetch makes fourteen calls whose included[] arrays overlap heavily. They are indexed into a single URN-keyed map rather than parsed one at a time.

Chosen
One graph, later responses win on conflict. An entity resolves regardless of which call carried it. On the live run 43 rows collapsed to 41 unique entities.
Alt
Parse each response independently. A Company referenced by a Position but only included in the education response would silently resolve to nothing.
Alt
First write wins. A sparse duplicate would overwrite a full projection and quietly lose fields.

Resolve through *elements, never included[]

Rest.li collections put the order in the reference array and the content in the entity array. Only one of them is ordered.

Chosen
Walk data['*elements'] and look each URN up. Preserves the reverse-chronological order LinkedIn intends.
Alt
Iterate included[] and filter by $type. Simpler, and scrambles a work history without ever erroring.
Detail
Some projections inline the element instead of referencing it, so the resolver accepts both.

Match $type by suffix

Entity lookups compare against profile.Position, not the fully-qualified com.linkedin.voyager.dash.identity.profile.Position.

Chosen
Suffix match. The package path shifts between API versions; the leaf name is stable.
Alt
Exact match on the full type. Correct and brittle — it breaks on a namespace move that changed nothing real.
Cost
A future somethingelse.Position would collide. Acceptable today; worth a comment when it stops being.

Return the URN rather than guess the label

Employment type arrives as urn:li:fsd_employmentType:18 and nothing in any capture maps that integer to “Full-time”.

Chosen
Expose employmentTypeUrn raw and document the gap. Returning the identifier we have beats fabricating one we do not.
Alt
Infer the table from observed examples. One or two data points would produce a mapping that is wrong for every value nobody happened to capture.
Alt
Drop the field. Throws away information a caller may be able to resolve themselves.

Partial dates stay partial

{year: 2022, month: null, day: null} is returned as-is rather than normalised to an ISO timestamp.

Chosen
Keep the shape LinkedIn actually has. Inventing 2022-01-01 makes a real January 1st indistinguishable from padding.
Alt
Normalise to ISO strings. Friendlier to consume, and lossy in a way the consumer cannot detect or undo.
Observed
Real consequence: a role with year-only dates computes a duration of 0 months. Honest, and visibly odd — which is the right kind of wrong.

Coverage as a first-class output

The response reports which sections were present, which came back empty and which failed, instead of returning [] for all three.

Chosen
Say what we know and what we do not. “No certifications” and “we could not determine certifications” are different answers and callers act on them differently.
Alt
Empty arrays everywhere. Simpler contract, and it silently converts a partial failure into a confident wrong answer.
Honest
The contract cannot distinguish “member has none” from “collection name is wrong and fails silently”, and the schema comment says so rather than implying otherwise.

Validate our own output at the boundary

extract-fixture.ts runs ProfileSchema.parse() on what the extractors produced before printing any of it.

Chosen
Parse our own output. Catches extractor bugs at the boundary rather than letting a malformed shape reach a caller.
Alt
Validate upstream input instead. Voyager's shape is the thing we do not control and cannot pin down; ours is.
Note
The 13 extraction tests run entirely against hand-written synthetic fixtures — no credentials, no network, no real personal data in the repo.

Capture once, iterate offline

fetch-profile.ts writes every raw response to capture/fixtures/<slug>/ so parser work costs zero upstream requests.

Chosen
Record, then replay from disk. The single most effective anti-ban measure here. The entire extraction layer was built and debugged against saved JSON.
Alt
Iterate against the live site. This is how a burner account reaches a checkpoint.
Cost
Empty responses are not written to disk, so the fixture path can never reproduce the empty coverage state. See below.

HTTP client, not a headless browser

The largest fork in the whole project: speak Voyager directly with undici, or drive a real browser with Playwright and read the DOM.

Chosen
Direct HTTP. Fourteen requests and about 25 seconds for a full profile, returning JSON. Trivially concurrent.
Alt
Playwright / Puppeteer. Genuinely better on detection — real TLS, real JS execution. Also 10–100× the cost per profile and a far larger surface to keep alive.
Alt
Browser extension against the user's own session. Sidesteps credential handling entirely, but cannot be a hosted API.
Cost
Node's TLS handshake does not look like a browser's, whatever the User-Agent claims.

A burner session, not an official integration

Worth stating plainly: this route exists because the supported ones do not cover the use case.

Chosen
Cookie session from a burner account, low volume, aggressive caching.
Alt
LinkedIn's official Marketing / Talent APIs. Partner-gated, and arbitrary profile lookup is not something they grant.
Alt
A commercial profile-data vendor. Buys reliability and moves the compliance question to a third party. Costs per lookup and returns their schema, not the source.
Cost
Terms-of-service exposure, account restriction risk, and a data-protection question that caching makes sharper, not softer.
06 — What's left

The remaining work, honestly stated

The extraction layer closed the largest open question. What is left is mostly assembly — plus two real bugs and one thing that cannot be fixed from inside this design.

  • To build
    The server itself

    src/server.ts does not exist. It needs the Fastify route, x-api-key auth, the profile cache (CACHE_TTL_SECONDS) and the upstream budget (UPSTREAM_MIN_INTERVAL_MS plus jitter). All four are already specified in config.ts; none are wired up. This is the last structural piece.

  • Bug
    The empty coverage state is unreachable

    fetch-profile.ts deliberately does not write empty collections to disk, and extract.ts records no coverage at all for a response that is undefined. So a fixture-driven extraction reports empty: (none) even when six collections genuinely came back empty upstream — the signal is printed to the console at fetch time and then lost. The server path must pass the empty responses through in memory, or fetch-profile must persist them.

  • Gap
    Four extracted sections are never printed

    extract-fixture.ts reports identity, experience, education, skills, certifications, languages and featured — but not projects, publications, honors or volunteer. The live run extracted a project that never appeared in the output. The extractor is fine; the reporting tool is incomplete.

  • Coverage
    The security modules are still untested

    16 tests pass: 13 on extraction, 3 on the Rest.li encoder. url-guard and ip-rules have none — and they are the two files where a regression is silent and serious. Every bypass named in their comments is a test waiting to be written.

  • Certain
    The queryId hash will rotate

    Only one is still load-bearing now that the card route is retired: QUERY_PROFILE_BY_VANITY, the slug-to-URN entry point. Everything after it is Rest.li paths, which are far more stable. That is a real reduction in fragility — the volatile surface went from four hashes plus an enum to one hash.

  • Unmitigated
    TLS fingerprinting sees through the headers

    A User-Agent makes a request look ordinary in a log. It does not defeat serious bot detection. LinkedIn can fingerprint the TLS ClientHello (JA3/JA4) and the HTTP/2 settings frame, and Node's handshake matches no browser regardless of what the header claims. Low volume, human-shaped pacing and internally consistent headers are the actual mitigation — and the clean run is evidence they are working, not evidence the risk is gone.

  • Radioactive
    Captures and fixtures are personal data

    capture/ holds live session cookies in the HARs and real profile records in the fixtures. .gitignore covers capture/, *.har and .env, and redact() strips credentials from anything headed for a log. The test fixtures are synthetic precisely so none of this has to be committed. All of that is one careless command away from being bypassed.

  • Open
    Legal and data-protection posture is undecided

    Scraping public profile data sits in genuinely contested territory — hiQ v. LinkedIn narrowed the CFAA reading but did not touch breach of contract, and says nothing about GDPR obligations once profile data is cached on a server. CACHE_TTL_SECONDS is an engineering knob that carries a retention policy with it.

07 — Concepts to read

What to study, and why it matters here

Grouped by the part of the problem they unlock. Every one of these is load-bearing somewhere in the code above.

Protocol shapewhy the payload looks like that
  • Rest.li protocol 2.0LinkedIn's own RPC framework, open-sourced. Its query grammar, compound keys and finder convention are the reason q=viewee and (a:b,c:d) exist at all. Read the wire protocol spec first.
  • URNs as entity identityurn:li:fsd_profile:<id> is a typed, globally addressable reference. Once you see the payload as a graph keyed by URN, included[] stops looking arbitrary.
  • Normalized vs embedded responsesThe vnd.linkedin.normalized+json accept header is the difference between a flat entity table and a nested tree. Compare with JSON:API's included and Redux's normalizr — same idea, same motivation.
  • Projections / decorationsdecorationId selects which fields come back. It is why the About section lives on one endpoint and not the other.
  • Persisted GraphQL queriesA queryId hash instead of a query body: smaller requests, and an allowlist that stops clients sending arbitrary queries. Also why those hashes rotate on every deploy.
  • Percent-encoding, preciselyRFC 3986's reserved vs unreserved sets, and why encoding depends on which component a character sits in. Exactly the 400-vs-200 distinction at the top of this page.
Reading the graphturning references back into data
  • Normalized client cachesnormalizr, Apollo's InMemoryCache, Relay's store. EntityGraph is a small hand-rolled one, and reading how the real ones handle identity and merging is the fastest way to see what it is missing.
  • Anti-corruption layerThe DDD pattern behind schema.ts: an explicit translation boundary so an unstable upstream model cannot leak into yours. This is the idea that makes a volatile API survivable.
  • Graph traversal with cyclesA Position references a Company which references Positions. Any resolver that walks this needs a visited set, and the bug it prevents is a hang, not an error.
  • Modelling partial and uncertain dataPartial dates, nullable fields, and the general principle that a type should be able to represent “unknown” without faking a value. Compare EDTF, the extended date/time format.
  • Parse, don't validateAlexis King's essay. Both url-guard and the extractors are the same move: return a narrower type that makes the invalid state unrepresentable, rather than checking and passing the original along.
  • Schema-first contractsZod at the boundary, and why validating your own output catches a different class of bug than validating your input.
Session & authwhy two cookies are a password
  • Double-submit cookie CSRFWhy it works without server state, and why it collapses the moment a client legitimately holds both halves — precisely this project's position.
  • SameSite, Secure, HttpOnlyThe attributes that decide whether a session cookie is reachable from JavaScript or a cross-site request. They explain what LinkedIn is defending against and what it is not.
  • Bearer vs proof-of-possession tokensli_at is a pure bearer credential: possession is authorisation. Token binding and DPoP are the designs that break that equivalence.
  • Cookie sharding and stickinesslidc pins a session to a datacenter. Worth understanding before deciding two cookies are enough.
Traffic analysishow any of this gets discovered
  • The HAR formatAn archive of full request/response pairs including headers. Learn to read it directly — and treat every one you produce as a credential store.
  • Intercepting proxiesmitmproxy, Burp, Charles. DevTools shows a browser's traffic; a proxy lets you replay and mutate it, which is how a parameter's meaning gets confirmed.
  • Bundle spelunkingQuery hashes, enum values and endpoint names are all present in the shipped JavaScript. Source maps, when exposed, turn guessing into reading.
  • Inference from naming conventionThe twelve collection names were derived from the reference keys on the Profile entity, not guessed. All twelve resolved. Learning to read a framework's conventions is how you predict endpoints you have never seen.
  • Differential probingChange one variable, observe the status code, keep the change that moved it. Slow, paced, and aborting on the first block signal.
Anti-botwhat actually identifies a client
  • TLS fingerprinting (JA3 / JA4)Cipher suites, extensions and their order form a fingerprint before a single HTTP byte is sent. The reason a spoofed User-Agent buys so little.
  • HTTP/2 fingerprintingThe Akamai fingerprint: SETTINGS values, window size, header order and priority frames. Another layer beneath the headers you control.
  • curl-impersonate & friendsClients built to reproduce a specific browser's handshake byte for byte. The honest answer to the limitation above — and an escalation worth weighing carefully.
  • Behavioural detectionRequest cadence, session length, ordering, coverage. The reason this project bursts and then pauses instead of sleeping uniformly.
  • Header order and coherenceReal clients send a stable header order and a self-consistent story. Sec-Fetch metadata, Accept-Language and the device blob all have to agree.
Web securitythe perimeter, and how it is defeated
  • SSRFPortSwigger's chapter, then a cloud metadata write-up. 169.254.169.254 is in the deny list for a specific historical reason worth knowing.
  • DNS rebinding & TOCTOUThe check-then-use race generalises far past DNS. Recognising the shape is the transferable skill.
  • URL parser confusionOrange Tsai's A New Era of SSRF and the WHATWG URL spec. Userinfo, backslashes, tab stripping, IDN homographs — every check in url-guard.ts maps to a published bypass.
  • Allowlist vs blocklistWhy endsWith('linkedin.com') accepts evil-linkedin.com, and why subdomain takeover means *.linkedin.com is not safe either.
  • Decompression bombs & resource limitsContent-Length is a claim, not a fact. Counting bytes as they arrive is why readCapped exists.
  • Secrets in transit and at restCredential-shaped log redaction, gitignore hygiene, and why comparing by hash beats printing a value.
Running itwhat the missing server needs
  • Token bucket & leaky bucketThe upstream budget is a shared resource protecting an account, not a server. Its shape differs from ordinary per-caller API rate limiting.
  • Jitter and backoffExponential backoff with full jitter — and the counter-intuitive point that here, evenly spaced retries are the tell.
  • Circuit breakersA checkpoint response means stop, not retry. Open the circuit and stay open; hammering a challenge is how a flagged account becomes a banned one.
  • Cache keys and TTLThe most effective ban mitigation available, and the place where a data-retention policy has to be decided.
  • Contract testing against fixturesCaptured responses are ground truth that goes stale silently. Something has to notice when the live shape diverges from the synthetic fixtures the tests trust.
  • Idempotency and request coalescingTen callers asking for the same profile at once should produce one upstream fetch, not ten. Single-flight is a small pattern with a large effect on ban risk.
Standingwhether to build it at all
  • hiQ Labs v. LinkedInThe Ninth Circuit on scraping public data and the CFAA — and, importantly, what it left untouched on remand.
  • Contract vs computer-misuse claimsTerms of service are a separate theory from unauthorised access. Winning one says nothing about the other.
  • GDPR and personal dataPublicly visible is not the same as free to store. Lawful basis, purpose limitation and retention all apply the moment a profile is cached.
